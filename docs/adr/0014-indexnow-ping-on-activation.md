# ADR 0014 — IndexNow Ping on Site Activation

**Date:** 2026-05-20  
**Status:** Decided

## Context

LLM assistants (ChatGPT via Bing, Claude via Brave, Perplexity via Bing+own) consume indexes that support the IndexNow protocol. Submitting a URL list to IndexNow is the fastest path to getting a freshly-activated tenant domain into both Bing and Brave within minutes rather than waiting for passive crawl.

There is currently no IndexNow integration anywhere in the codebase. The key architectural concerns are:
- Where in the pipeline is a site definitively "indexable" (robots open, status=live)?
- A shared IndexNow key served across all tenant domains is a cross-domain footprint signal.
- IndexNow submissions are external HTTP calls — they are side-effecting and need failure handling.
- A wave of 3-5 sites can promote to live in a short window; submissions must be batched or staggered.

## Decision

### 1. Trigger point

The ping fires from `promoteSiteToLive()` in `apps/operator/app/operator/sites/[id]/go-live-actions.ts`. This is the only place in the codebase that transitions `sites.status` to `'live'` via a human operator action, and it follows the `robotsDisallow=false` gate enforced by the GoLiveChecklist. Rather than inline the HTTP call inside the server action, `promoteSiteToLive` inserts an `agent_events` row of type `site.activated` targeting a new `indexnow-submitter` agent. The cron worker claims it via the normal `FOR UPDATE SKIP LOCKED` path.

The `site.deployed` event (emitted by site-builder at step 8) is intentionally NOT the trigger. At that point the site is still `warming`, robots are still blocked, and `robotsDisallow` may not yet be flipped. Firing IndexNow then would submit URLs that return 403/noindex to the crawler — potentially harmful to the submission record.

### 2. Key strategy

Per-site keys. IndexNow keys are public (served at `{domain}/{key}.txt`) and the submitting host is recorded in the submission. A shared key served from a single file would directly link all tenant domains to one operator — a clear footprint signal.

**Key storage:** `indexnow_key TEXT` column on the `sites` table, populated when the row is first promoted to `live`. The key is a 32-character hex string generated at promotion time (crypto.randomBytes(16).toString('hex')). It never changes after creation (idempotent on re-run via COALESCE).

**Key file serving:** A new route handler at `apps/site-host/app/[key].txt/route.ts` reads the current host via `resolveCurrentSite()`, fetches `site.indexnow_key`, and returns `text/plain` with the key value. Returns 404 if the key is not set or the host does not resolve. This is a per-host dynamic route, consistent with how `robots.ts` and `sitemap.ts` work.

### 3. URL set and change detection

**First activation:** submit the full sitemap URL set — identical to the URLs generated by `apps/site-host/app/sitemap.ts`. The `indexnow-submitter` agent derives these from the Sanity bundle at run time (same `sanityToBundle` call) rather than fetching `/sitemap.xml`, to avoid a cold-start round-trip.

**Subsequent content updates:** when `seo-operator` applies a `new_info_page` recommendation (or any Sanity patch that adds/replaces pages), it emits a `site.content.updated` event with a `urls: string[]` payload containing only the changed URL(s). The `indexnow-submitter` agent handles both event types: `site.activated` submits the full set; `site.content.updated` submits the delta list.

Change detection does not require a separate diff mechanism — the applying agent already knows exactly which URLs changed (it just wrote them) and stamps them in the event payload.

### 4. Approval gate

`autoApproveRule`. Justification: IndexNow submissions are low-risk, reversible in the sense that a bad submission is ignored by the index (not harmful to the site), have no cost dimension, and gating them on human approval defeats the purpose (the operator already made the side-effecting decision by clicking "Mark site as live"). Add an `auto_approve_rules` row with `kind = 'indexnow_submit'` seeded in the next migration. Document this in the migration comment.

The `agentApprovals` queue is still used for the intermediate state (the row is created then immediately auto-approved), so the audit trail exists.

### 5. Failure and rate handling

The `indexnow-submitter` agent uses `BaseAgent`'s dedupe_key for idempotency (`indexnow:${siteId}:${eventType}:${epoch}`). Response handling:

- 200/202: success, mark event claimed.
- 400/422: log + dead-letter (payload problem, not transient). Do not retry.
- 403: log + dead-letter (key file not yet resolvable — site may not have propagated through Vercel edge yet). Operator can re-queue after confirming DNS.
- 429: the agent_events reaper handles re-queue with exponential backoff. The agent returns a retriable error so the row re-enters the queue.
- Network failure: same as 429 path.

Wave batching: IndexNow accepts up to 10,000 URLs per submission call. For a wave of 5 sites with ~30 pages each, that is 150 URLs — easily one call per site. The `operator-tick` cron fan-out naturally introduces per-tick spacing (one agent_events row per site), so the submissions are staggered by the tick interval (~1 min) without special throttling logic in the agent.

Both Bing and Brave support the same IndexNow endpoint format (`https://api.indexnow.org/indexnow`); a single POST per site covers both.

### 6. Secrets and config

No secret. The IndexNow key is public by definition. The per-site key lives in `sites.indexnow_key` (DB). No env var needed beyond what the DB connection already provides.

Optional config: `INDEXNOW_ENDPOINT` env var defaulting to `https://api.indexnow.org/indexnow`. This allows pointing at the Bing-specific or Brave-specific endpoint if needed in future, or a test endpoint in dev.

## Alternatives considered

**A. Inline the ping inside `promoteSiteToLive` server action** — simpler, but violates the one-way rule (apps cannot import packages/agents directly), puts network I/O inside a server action that must complete before the page reloads, and provides no retry/backoff.

**B. Shared key, single file in site-host public/** — operationally simpler, but the key file would be served at every tenant domain from the same file, and the IndexNow API records the submitting host. Any operator doing competitive research could observe all our domains share a key. Rejected: footprint risk.

**C. Hook into `site.deployed` (site-builder step 8)** — fires too early; robots are still blocked. Would submit unindexable URLs.

**D. New step inside SiteBuilder.execute()** — bakes a post-deploy action into the builder, which already has 8 steps and is not the right owner of activation state. SiteBuilder sets status=`warming`, not `live`.

## Consequences

**New files:**
- `packages/agents/src/indexnow-submitter/index.ts` (new agent)
- `packages/integrations/src/indexnow/index.ts` (new integration seam)
- `apps/site-host/app/[key].txt/route.ts` (key file handler)
- `packages/db/migrations/NNNN_sites_indexnow_key.sql` (add `indexnow_key` column)

**Modified files:**
- `apps/operator/app/operator/sites/[id]/go-live-actions.ts` — emit `site.activated` event after status flip
- `packages/agents/src/registry.ts` — register `indexnow-submitter`
- Seed migration or `autoApproveRules` insert for `kind = 'indexnow_submit'`

**No changes to:** site-builder, content-engine, seo-meta, site-context, sitemap.ts, robots.ts (beyond the new route handler).
